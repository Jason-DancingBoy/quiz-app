# 面试官手册：AI Agent 开发岗模拟面试（李炯炫定制版）

> 更新日期：2026-08-06
> 面试形式：纯口答 + 口述设计题（不写代码）
> 建议时长：55–60 分钟
> 定位：**中级为主，带一点高级架构题；Live-Edit 是全场最重环节**

---

## 一、面试信息总览

### 面试者画像（简历已核实）

- 中国地质大学（北京）本科，C++ 开发工程师背景（2026.02–2026.05 世炬网络，基站 OAM 自愈模块）
- 两个 Agent 项目：
  - **Quiz-App**：端到端 RAG 智能出题系统（本仓库，已完整部署交付）——**面试官即该项目的部署者，掌握全部代码细节**
  - **Live-Edit**：AI Agent 代码编辑系统（自研 Agent Loop，已 clone 逐行核实）——**面试重点**
- 定位判断：**实际水平明显超过初级**——核心能力真实且扎实，简历存在「包装措辞」但非造假（详见第二节）

### 面试目标

不是「考察他会不会基础概念」（他早会了），而是验证三件事：
1. **诚实度**：简历上没真落地的部分，他是否主动承认（最锋利的第一题）
2. **落地 vs 概念**：能否讲出实现细节，而非背概念（Live-Edit 是主战场）
3. **工程与架构素养**：生产化思维、失败模式、框架取舍

### 评分维度

| 维度 | 权重 |
|---|---|
| 诚实度（第一题直接验证） | 20% |
| 概念深度（记忆系统/RAGAS/评估） | 30% |
| 工程意识（限流/成本/失败模式） | 25% |
| 架构判断（自研vs框架/multi-agent） | 15% |
| 表达与思维 | 10% |

## 四、完整问题清单（按流程顺序）

### 阶段 1：破冰 + 项目概述（5 min）

**Q0. 「先讲讲你的两个项目吧——Live-Edit 和 Quiz-App，各自解决了什么问题、你负责哪部分？」**
- 听点：能否 2-3 分钟讲清「问题 → 方案 → 我的贡献」；**记录他重点讲的哪个项目**（通常是参与度最高的，后续优先深挖）
- 若他 5 分钟还没进正题，温和打断「我们后面会细挖，先帮我建立整体印象」

### 阶段 2：Quiz-App 验证（12 min）

**🔴 Q1. 「你简历写了评测 Context Relevancy / Context Precision / Faithfulness 三个 RAGAS 指标。分别说说这三个各自测什么？你在项目里实际落地了哪几个？」**
- 概念（答对是前提）：
  - Context Relevancy = 检索到的上下文与问题的相关性（是否答非所问）
  - Context Precision = 检索结果中相关片段是否排在前面（排序质量）
  - Faithfulness = 回答是否忠于检索上下文（是否编造）
- **验证点**：代码只实现了 Faithfulness。期望他诚实说「实际只落了 Faithfulness，另外两个研究过，但我的场景是生成题不是问答，意义不大」→ **诚实 + 有判断力，满分**
- 危险回答：「三个都用了，RAGAS 库自带的」→ 代码里没有，简历注水
- 追问：「你的格式合规率和质量分是 RAGAS 的还是自研的？」→ 期望：自研（`check_format_compliance` + `score_question_quality`，LLM-as-judge 逐题 1-5 分）

**🟡 Q2. 「这个项目生产部署了，限流 50 次/天是怎么实现的？如果开两个 worker 进程会怎样？」**
- 期望：内存计数 + 主动指出「多进程会失效、重启清零，应该用 Redis/DB」→ 工程意识强
- 危险：声称「存 DB/Redis」→ 与代码不符

**✅ Q3. 「文档很小的时候，你也走完整 RAG 吗？」**
- 期望：能提到「短文档（<6000 字符）直接全文塞 prompt，跳过检索」→ 简历没写这个细节，答出来是真做过
- 追问：「那超大的文档（>500 chunk）呢？」→ 期望：分层采样（30 桶随机 + 文本重叠去重），且跳过 embedding

**✅ Q4. 「出题为什么用『切段 + 逐题并行调 LLM』，而不是一次调用生成全部题？」**
- 期望：逐题并行保证题目覆盖不同知识点 + 可 SSE 逐题推送 + 单题失败不影响全局；一次生成省 token 但多样性差、失败难重试
- 深挖：「你生成题时是几路并行？并行打满 API 怎么办？」→ 期望：`asyncio.as_completed` + 留意限流/成本

### 阶段 3：Live-Edit 验证（20 min，全场重点）

> 九道题按「Loop 本体 → 记忆 → 评估 → 安全 → 细节」递进。Q5–Q9 是简历显性内容，Q10–Q13 是简历没写的隐藏细节（最强试金石）。

**✅ Q5. Agent Loop 本体**
「你的 Agent 循环有哪些退出条件？如果模型连续几轮只读不写，你会怎么处理？」
- 期望（前半）：`max_rounds`(默认15) + 无工具调用自动退出 + 用户取消中断
- 期望（后半，隐藏细节）：deep 模式下连续 `_write_less_rounds ≥ 3` 轮只读不写 → 主动注入「别再搜索了，直接 edit_file」的 nudge 提示
- 判断：**他若能自己讲出 nudge 机制 = 真做过；只讲三个退出条件 = 背的简历**

**✅ Q6. 记忆系统（重头戏，拆三个追问）**

Q6a. 「三阶记忆系统，短时记忆『超窗截断 + 增量摘要』具体怎么触发的？」
- 期望：讲出三档策略——轮数少（≤`max_full_rounds`）不动 → 超窗只截断 → 截断 + LLM 摘要，**轮数太多只截断不再花 token 摘要** → 说明真做过

Q6b. 「长时记忆『余弦 + 时效衰减 + 命中频次加权』，加权公式长什么样？」
- 期望：`final = cosine × exp(-rate × days) + hit_weight × min(hit, 10)` 或接近的表述
- 深挖：「命中次数为什么封顶 10？」→ 防热门 chunk 无限霸榜

Q6c. 「低层检索为空自动降级是什么意思？」
- 期望：L2 长时记忆无结果 → 降级到 L3 项目知识库（`if not memories_hit`）；L3 还按 SHA256 检测文件变更增量同步

**✅ Q7. 自愈评估**
「评估五阶段是什么？introspect（LLM 自查）判定『通过』的标准是什么？」
- 期望：lint→test→preview→introspect→html_diff + 「让 LLM 判断改动是否达成用户目标」
- 高级追问：「introspect 用字符串判断『通过』两个字，会不会误判？怎么改？」→ 代码是 `passed = "通过" in text[:100] and "未通过" not in text[:100]`，看能否指出脆弱性
- 期望改进：结构化输出（JSON 布尔字段）/ 正则 / 多判据

**✅ Q8. 崩溃恢复**
「/continue 断点恢复，具体怎么保证崩溃后对话还能继续？」
- 期望：每轮持久化 messages 到 SQLite + worktree 在 TTL 内保留 + 崩溃留下的孤儿 tool_use 会被修复（Anthropic API 要求 tool_use 紧跟 tool_result）
- 深挖：「什么情况下恢复会失败？」→ 能想到「worktree 被 TTL 清理 / 会话过期（SessionStore TTL 30 分钟）」加分

**🟡 Q9. Tool Registry 与 Schema**
「你说工具注册表『自动生成』JSON Schema——具体怎么生成的？怎么保证参数校验？」
- 期望：诚实说「Schema 是手写的 input_schema，不是从签名自动推断」+ 解释手动写更可控（描述质量影响 LLM 选工具）
- 危险：含糊其辞「用了 pydantic」→ 代码里没有
- 追问：「7 个工具怎么管优先级和模式（quick/deep/qa）的？」→ 期望：priority 冲突覆盖 + modes 可见性过滤

**🟡 Q10. 安全层绕过（高级安全题，最能拉开差距）**
「safety.py 的 shell 白名单用 startswith 匹配前缀，那 `ls; rm -rf /` 这种命令会怎样？」
- 代码真相：`startswith("ls ")` 命中 → `is_safe=True` → **跳过危险正则检查** → 分号注入可以绕过白名单
- 期望：他能指出「白名单前缀 + 分隔符注入」是经典绕过方式，并给出加固方案（命令解析后逐 token 校验 / 禁止 `;` `&&` `|` / 白名单改执行器而非字符串匹配）
- 危险：完全想不到 shell=True + 前缀匹配有注入面
- 加分方向：提到「即使白名单安全，LLM 生成的命令也该按『不信任输入』对待」

**✅ Q11. Provider 层工程细节**
「LLM 调用你处理了哪些失败？429 限流怎么退避的？流式返回 tool_use 的参数是怎么拼的？」
- 代码真相：`_RetryableError`（429 读 Retry-After + 5xx）vs `_FatalError` 区分，max_retries=3；流式 SSE 中 tool_use 的 JSON 参数是分块 `_partial_json` 增量累积的
- 期望：能讲出「可重试错误（限流/5xx）和不可重试错误（4xx 参数错误）要分开处理」→ 工程素养分水岭
- 加分方向：知道「读 Retry-After 头而不是死等固定时间」

**✅ Q12. 审批拒绝的连锁处理**
「用户拒绝了其中一个工具调用，但你这一轮同时发了好几个工具，会发生什么？」
- 代码真相：一个被拒 → 后续所有未处理的 tool_use 也要补 `tool_result`（否则 Anthropic API 直接 400「tool_use ids without tool_result」）
- 期望：讲出「必须给每个 tool_use 配对 tool_result，哪怕内容是『已跳过』」→ 说明他真的踩过 API 400 的坑

**✅ Q13. edit_file 的模糊匹配**
「edit_file 如果 old_string 没找到，或匹配多处，你怎么处理？」
- 代码真相：没找到 → 返回文件开头预览；多处 → 报告行号 + 上下文片段让 LLM 缩小范围；还有「空白归一化」匹配（忽略空格差异再找一次）
- 期望：能讲出「把错误信息喂回给 LLM 让它自纠」的设计理念

### 阶段 4：高级架构题（10 min）

**Q14. 「你自研 Agent Loop 不用 LangGraph，为什么？什么场景你会选框架？」**
- 期望：自研理由 = 深度控制（审批、断点、审计、多模式）+ 学习成本可控；框架理由 = 团队协作、标准生态、多 Agent 编排
- 判断：能说出「自研 ≠ 高级，是取舍」→ 真懂

**Q15. 「两个 Agent 协作『读代码 → 改代码 → 跑测试』，你怎么分工和通信？」**
- 期望：职责分离（读/改/测）+ 共享状态（worktree/文件系统是事实源）+ 结构化结果交接
- 深挖：「改代码的 Agent 和跑测试的 Agent 各说各话怎么办？」→ 共享仓库/文件作为唯一事实源

**Q16. 「Live-Edit 上生产，最可能挂的三个点是什么？你怎么兜底？」**
- 期望（参考）：① 死循环/token 爆炸（有 max_rounds）② 工具误操作破坏代码（有 worktree+safety）③ LLM 输出畸形 tool_use（有 _repair_messages）④ 成本失控
- 判断：能否用自己的机制举例「我已经防了 X」→ 工程直觉强

**Q17. 「Agent 输出每次不一样，你怎么知道这次改动是变好还是变坏？」**
- 期望：把 Quiz-App 的评测思路迁移——固定场景集 + 指标（任务成功率/工具调用效率/结果匹配）+ 回归对比
- 判断：这是高级题，答出合理思路即加分

### 阶段 5：收尾（3 min）

**Q18. 「你简历 2026.02–2026.05 在 C++ 岗，怎么转到 AI Agent 的？未来想往哪个方向深耕？」**
- 听点：转行动机是否真实（做项目 > 说空话）；对方向的认知（应用层/框架层/模型层）

**Q19. 「你有什么想问我的？」**
- 听点：问技术细节（加分）还是只问薪资福利（中性）；对岗位的理解深度

- Q1 诚实承认只落 Faithfulness + Q6b 记忆公式讲得清 + Q10 能指出白名单绕过 → **实际水平中级偏上**

- 主动讲到 ≥3 个 → 项目真实参与度极高
- 只讲出 1 个 → 参与过但可能是照教程复刻
- 0 个 → 简历水分大，需重点怀疑

**录用参考**：总分 ≥ 3.5 → 通过（中级）；≥ 4.5 → 超出预期

## 六、面试官知识速查（面试前必读）

### 必须吃透（1–2 天可完成）
1. **RAGAS 三指标**：Context Relevancy（相关性）/ Context Precision（排序质量）/ Faithfulness（忠于上下文）——记住 Quiz-App 只落了 Faithfulness
2. **记忆系统三档策略**：max_full_rounds（不动）→ max_stripped_rounds（只截断）→ max_summary_rounds（截断+摘要，再超只截断）
3. **L2 加权公式**：`cosine × exp(-rate×days) + hit_weight × min(hit, 10)`
4. **Agent Loop 三退出条件 + nudge**：max_rounds / 无工具调用 / 用户取消；连续只读会触发「直接改」引导
5. **Function Calling 原理**：声明 schema → LLM 输出 JSON → 程序执行 → 回填
6. **Anthropic tool_use/tool_result 配对规则**：崩溃或被拒会产生孤儿 tool_use，必须补齐配对（`_repair_messages` / 审批拒绝 fill 存在的意义）
7. **RAG 全链路**：你已精通（Quiz-App 就是标准答案）
